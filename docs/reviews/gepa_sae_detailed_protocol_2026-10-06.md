## 1. 무엇을 바꾸나

**여러 답변 쌍에서 반복되는 차이를 찾아 GEPA의 피드백으로 제공하면, 정상 질문을 보존하면서 필요한 교정을 더 잘 늘릴 수 있는가?**

첫 버전은 최종 답변의 system prompt만 최적화한다. 생성 모델, Well 평가 기준, 수치 점수, 추론 설정은 고정한다. SAE는 의료 사실을 판정하거나 평가 점수를 계산하는 모델이 아니다. 특징 설명은 프롬프트 수정에 참고할 정보이며 정답 규칙으로 강제하지 않는다.

검증기 최적화, NLA/AO, DPO를 한 번에 넣지 않는다. 먼저 SAE에서 얻은 정보의 추가 가치를 구분하고, 확인되면 각 단계로 확장한다. “GEPA가 규칙을 적게 찾아서 실패한다”는 주장은 전제하지 않는다.

## 2. 가져오는 부분과 새로 만드는 부분

WIMHF는 답변 임베딩 차이에 SAE를 학습하고, 특징이 강한 답변 쌍을 LLM에 보여 설명을 만든다. 설명이 별도 쌍의 활성값과 맞는지 확인한 뒤 선호와의 관계를 분석한다. 원 논문은 주관적 선호 중심이므로 의료 사실 판별까지 검증한 것은 아니다. [WIMHF 원문](https://arxiv.org/html/2510.26202)

공식 코드의 후속 업데이트는 질문을 포함한 로컬 임베딩을 권하지만 전체 후속 평가 재실행은 하지 않았다고 밝힌다. 이번에는 그 경로를 택하고 원 논문 그대로의 재현과 구분한다. [WIMHF 공식 코드](https://github.com/rmovva/wimhf)

**우리가 추가할 부분:** 특징 발견 결과를 GEPA의 실행 피드백에 연결하고, 미사용 질문에서 교정·보존을 함께 개선하는지 평가한다. 선호 설명을 자동으로 규범적 루브릭이나 사실 정답으로 바꾸지 않는다.

2. **특징 발견용 실험:** CREPE opt_train에서 목표 200 FPQ + 200 정상 질문, Cancer-Myth opt_train 30+30을 사용한다. 합계 최대 460질문이며 질문/통념/출처 그룹을 먼저 감사한다. 그룹 제약으로 정확한 수가 안 맞으면 실제 수를 기록하고 가중치를 사용한다.
3. **도메인 전이 대조:** CREPE만으로 발견한 특징과 Cancer-Myth를 포함해 발견한 특징을 비교한다. 두 경우 모두 기준 GEPA·텍스트 피드백 조건에 같은 자료 접근을 제공한다.

위 400개 CREPE 선정은 아직 수행하지 않았다. test에서 답변을 가져와 수를 채우지 않는다. Cancer-Myth 기존 test와 특히 반복 독해한 199문항은 새 독립 시험셋이 아니다. 기존 결과와의 연결은 탐색 평가로만 보고한다. 새 최종 평가를 주장하려면 노출 이력을 감사하고 추가 미사용 자료 또는 노출을 명시한 전이 평가를 확보해야 한다.

## 4. 분할과 누출 방지

| 구역 | 사용 | 금지 |
|---|---|---|
| feature_fit | 임베딩 전처리·SAE 학습, 설명 예시, 선호 연관 추정 | dev/test 포함 |
| feature_check | 설명 일치도·특징 안정성 확인, 특징 선택 | 최종 성능 시험이라고 부르기 |
| opt_train | GEPA 반성용 질문·답변·고정 기준 답변 | 평가 문항의 정답 이용 |
| opt_dev | 후보 프롬프트 선택 | SAE 학습, 특징 설명·라이브러리 수정 |
| final_test | 최종 조건 비교 | 후보·특징·프롬프트 선택 |

feature_fit/check는 opt_train 내부를 질문 그룹 단위로 약 75/25로 나눈다. 둘 다 GEPA의 학습 자료이며, check는 **특징 학습에 대해서만** 분리된 검증 자료다. 같은 질문의 모든 답변, A/B 뒤집기, 수정 질문은 같은 구역에 둔다. 그룹별 규모와 FPQ/NFP 수를 manifest에 기록한다. 데이터 종류별 특징의 부호 차이를 보되 개별 질문의 라벨을 추론 시 제공하지 않는다.

같은 질문에서 만든 여러 쌍은 독립 표본이 아니다. 문항별 총 가중치를 같게 하고 통계적 불확실성도 질문/출처 그룹 단위로 계산한다. 기존에 test 분석으로 수정한 D/E 등 지시는 새로운 깨끗한 데이터 생성 조건으로 쓰지 않는다. 저장 답변을 재사용할 때 질문뿐 아니라 생성 프롬프트의 개발 이력도 확인한다.

## 5. 어떤 답변 쌍을 만드나

각 학습 질문에 사전에 고정한 3조건을 적용한다: Plain, 고정 균형 지시, 전제 검토 CoT. 이미 호환되는 저장 답변이 있으면 재사용한다. 모델 버전·추론 설정·프롬프트 해시·생성 시각을 보존한다.

한 질문에서 기본 두 쌍을 만든다.

- 균형 지시 답변 vs Plain 답변.
- 전제 검토 답변 vs Plain 답변.

잘못된 답변만 일부러 넣거나 성공/실패 쌍만 골라 SAE에 주지 않는다. 둘 다 성공, 둘 다 실패, 점수가 같은 쌍도 특징 발견에는 포함한다. 생성 조건의 이름·모델명·점수·FPQ/NFP 라벨은 임베딩 입력에서 제외한다. A/B 위치는 재현 가능한 난수로 섞고 방향을 기록한다.

SAE 학습과 선호 분석을 분리한다.

- **SAE 학습:** 답변의 차이를 학습하므로 선호 라벨이 필요 없다.
- **선호 분석:** 고정 Well 점수와 판독으로 어떤 차이가 더 좋은 답변과 관련되는지 본다. 점수 차이만으로 원인을 단정하지 않는다.
- 점수 동점, 양쪽 장단점이 다른 쌍, 정상적 부정 답변 등 경계 사례는 `tie/uncertain`으로 보관하고 이진 선호 회귀에서 제외한다. 버린 비율을 함께 보고한다.
- 사람이 판정하지 않은 자료는 human feedback으로 부르지 않는다. AI 평가의 오류를 특징이 학습할 수 있으므로 조건명을 가린 독립 표본 검토를 한다.

초기 모든 학습 질문의 Well 판정을 반복할 필요는 없다. 일단 저장 평가와 사전 선정한 경계·비경계 감사 표본으로 라벨 품질을 점검하고, 필요한 경우에만 재채점한다.

## 6. 임베딩과 SAE의 초기 설정

| 요소 | 첫 설정안 | 이유/주의 |
|---|---|---|
| 임베딩 | `Qwen/Qwen3-Embedding-8B`, 로컬 경로 | 설치·메모리 확인 필요. 불가하면 작은 임베딩으로 모든 조건을 일관되게 바꾸고 기록 |
| 입력 | 고정 instruction + 원 질문 + 답변 | 개인 상황과 추론을 구분할 문맥 포함. 정답 주석·선호·모델명 제외 |
| SAE 입력 | `emb(question, A) - emb(question, B)` | 같은 질문 내 답변 차이 |
| 방향 | 원 방향과 반대 방향을 fit에 함께 포함 | chosen 방향으로만 학습하지 않음. 같은 그룹/가중치 처리 |
| 크기 | 16특징, 평균 활성 목표 2 | 작은 자료에서 시작하는 제안값. 원 논문 설정 재현이라고 주장하지 않음 |
| 학습 seed | 3개 | 설명과 활성 패턴의 안정성 확인 |
| 전처리 | feature_fit에서만 통계 추정·고정 | check/dev/test로 정규화나 활성 문턱을 맞추지 않음 |
| 추론 | 동결된 encoder/활성 기준 | 평가 배치 구성에 따라 특징 선택이 달라지지 않게 확인 |

공식 구현의 signed feature 처리와 BatchTopK 추론을 먼저 확인한다. 방향 반전 및 배치 의존성 검사를 통과해야 GEPA에 연결한다. 32특징 등 용량 변경은 별도 개발 비교로 기록한다. 많은 특징 수 자체를 성공 기준으로 삼지 않는다.

임베딩에서 사실 정오가 잘 드러나지 않을 수 있다. SAE가 문체·길이·거절 방식만 구별하면 그 결과를 보고하고, 의료 정확도를 발견했다고 이름 붙이지 않는다.

## 7. 특징을 설명하고 선택하는 절차

1. 각 특징이 강한 학습 예시를 여러 질문 그룹에서 선택한다. 한 질문의 변형만으로 설명하지 않는다.
2. 일반 LLM에 답변 쌍의 공통적인 차이를 설명하게 한다. 처음 설명할 때 어느 답변이 선호됐는지는 감춘다.
3. feature_check에서 설명만 본 LLM이 어느 답변에 해당 특징이 더 있는지 판정한다. 이 판정이 실제 특징의 활성 방향과 일치하는지 검사한다.
4. 선호와의 연관은 별도로 추정한다. 길이 차이를 통제하고, FPQ/NFP·도메인별로 부호가 달라지는지 기록한다. 여러 특징의 검정을 보정하고 질문 그룹 단위 불확실성을 보고한다.
5. 세 SAE seed에서 활성 패턴과 설명이 안정적인지 확인한다. 실패한 특징에 그럴듯한 이름만 붙여 사용하지 않는다.

첫 GEPA에 넣을 라이브러리는 **최대 8특징**, 한 피드백에 노출할 것은 **최대 3특징**으로 제한한다. 통과한 특징이 더 적으면 그만큼만 사용한다. 일반화 효과를 보여주려고 특징을 임의로 늘리지 않는다.

특징 기록은 설명, 대표 예시 ID, 일치도, 그룹 수, 선호 연관과 구간, 길이 연관, 데이터별 부호, 불확실성으로 구성한다. “FPQ에서 유익/NFP에서 해로움”처럼 단순 반박 성향을 나타내는 특징도 삭제하지 않고 조건부 연관으로 보고한다. 전역적으로 반박을 늘리라는 지시로 바꾸지 않는다.

## 8. GEPA 안에서 새 답변과 무엇을 비교하나

**각 opt_train 질문의 고정 Plain 답변을 기준 답변으로 저장한다.** 후보 프롬프트가 만든 답변과 이 답변의 임베딩 차이를 SAE에 넣는다. 정답 답변을 기준으로 쓰지 않는다. 기준 답변이 틀릴 수 있으며, 기준 답변보다 다르다는 것이 더 좋다는 뜻은 아니다.

```text
후보 프롬프트 + 질문 → 새 답변 → 고정 Well 평가 → 기존 점수
                         │
                         └→ 같은 질문의 고정 Plain 답변과 비교
                              → 동결 SAE 특징
                              → 검증한 특징 설명·대표 사례
                              → GEPA 반성 입력에 추가
```

초기 후보가 Plain과 같으면 차이가 작을 수 있다. 이때 관련 특징이 없다고 기록하고 억지로 3개를 채우지 않는다. 새로운 답변이 학습 범위를 벗어나거나 활성 근거가 약하면 추가 피드백을 생략한다. opt_dev와 final_test의 점수 계산에는 SAE가 필요 없다.

특징 목록은 한 GEPA 실행 중에 다시 학습하지 않는다. 첫 실험은 “동결된 특징 라이브러리가 도움이 되는가”를 본다. 온라인 재학습은 별도 후속 조건이다.

## 9. 피드백의 정확한 모양

기존 `question / answer / raw_score / score_explanation`을 그대로 유지하고 아래를 추가한다.

```json
{
  "anchor_answer": "같은 학습 질문의 고정 Plain 답변",
  "feature_feedback": [
    {
      "feature_id": "f07",
      "description": "특징 발견으로 얻고 검증한 설명",
      "relative_to_anchor": "more / less / unclear",
      "candidate_excerpt": "새 답변에서 해당 설명의 근거가 되는 구절",
      "evidence_pair_ids": ["training_pair_004"],
      "preference_association": "학습 자료에서 관찰한 연관과 불확실성",
      "caveat": "이 특징만으로 답변의 사실성이나 점수를 결정하지 말 것"
    }
  ]
}
```

인용 구절은 원 답변의 부분 문자열인지 검사한다. 특징과 인용의 연결은 추가 LLM 판독이므로 자동 정답이 아니다. 단순 복사 가능한 최종 프롬프트 규칙을 미리 작성해 주는 대신, 반성 모델이 여러 성공·실패 사례를 고려하게 한다.

**예시(실제 발견 결과 아님):** 후보 답변은 요청에 직접 답하고, 기준 답변은 요청 대신 확인을 반복했다. 해당 특징은 정상 질문의 좋은 점수와 연관됐지만, FPQ에서는 목표 오류를 고치지 않은 채 직접 답한 사례도 있었다. 이런 피드백은 “무조건 직접 답하라”로 요약하면 안 된다.

최종 추론에는 최적화된 prompt와 사용자 질문만 필요하다. 학습용 기준 답변, SAE, 선호 라벨, 정답 주석은 사용하지 않는다. 추론 때도 특징 검토를 돌리는 방법은 별도 시스템이다.

## 10. 비교 조건과 공정성

| 조건 | 기존 GEPA 피드백에 추가하는 것 | 가르는 질문 |
|---|---|---|
| G0 원래 GEPA | 없음 | 기존 기준선 |
| G1 답변 쌍 피드백 | 같은 기준 답변과 고정된 학습 답변 쌍 | 개선이 단지 추가 예시 때문인가 |
| G2 텍스트 특징 피드백 | 같은 답변 풀에서 LLM이 텍스트로 발견·검증한 특징 | SAE 없이 요약해도 되는가 |
| G3 SAE 특징 피드백 | SAE로 발견·검증한 특징 | SAE 발견 과정의 추가 가치가 있는가 |

G1–G3에는 동일 학습 질문·답변·선호·고정 기준 답변에 대한 접근을 준다. G0 대비 향상만으로 SAE의 효과를 주장하지 않는다. 핵심 비교는 G3 대 G2이며 G1도 확인한다. G2도 예시를 조금만 보여주지 않고 같은 풀을 배치 요약·통합할 수 있게 한다.

G2/G3의 특징 수 상한, 피드백 길이 상한, 해석/주석 예산을 맞춘다. 첫 제안값은 특징 최대 8개, 매 반성 샘플에 최대 3개, 추가 피드백 최대 800토큰, 최종 system prompt 최대 512토큰이다. 초과 후보의 처리 규칙을 모든 조건에 동일 적용한다. 임의 절단 대신 재제안/실패 처리하고 횟수를 기록한다.

길이 제한을 넣은 비교는 과거 Well 기본 설정과 다르므로, G0도 같은 제한에서 새로 돌린다. 이전 GEPA의 숫자만 대조군으로 가져오지 않는다. 최적화 평가 횟수가 같아도 특징 발견 비용은 다르므로 그 비용까지 별도 보고한다.

첫 비교의 수치 목표는 기존과 같이 FPQ와 NFP 각각의 평균 Well/5에 같은 가중치를 주는 것이다. 학습·개발에 동일 개수를 쓰면 기존 평균을 유지할 수 있다. 불균형을 쓸 경우 평가 집계가 이를 구현하는지 확인하고 별도 프로토콜로 기록한다. SAE 점수를 보상에 더하지 않는다.

## 11. 규모와 중단 기준

| 단계 | 제안 규모 | 완료 조건 |
|---|---|---|
| P0 자료/코드 점검 | 새 호출 없음 | 그룹·노출·답변·평가·버전 원장, 피드백 삽입 위치 확인 |
| P1 연결 확인 | Cancer 학습 60개, 작은 개발 표본 | 방향·누출·인용·캐시·GEPA 피드백 전달 검사 통과 |
| P2 특징 발견 | 최대 460질문 × 3답변, 기본 2쌍/질문 | 독립 check에서 특징 설명이 활성과 맞는지 확인 |
| P3 저예산 최적화 | G0–G3 각 최대 100 metric calls, seed 1개 | 비용과 출력 정상성 및 개발 개선 가능성 점검 |
| P4 본 비교 | G0/G2/G3 각 최대 500 metric calls, GEPA seed 3개 | 같은 개발 기준으로 선택, 최종 반복 평가 |
| P5 확장 | 공개 모델, CREPE/Cancer 전이, 일반 QA | 미사용 자료에서 성능·비용·보존 평가 |

`metric call`은 보통 답변 생성과 채점을 포함하며 CLI 호출 1회와 같지 않다. P2를 전부 새로 생성하면 최대 1,380답변, 최대 920기본 쌍이다. 저장 답변 재사용분을 먼저 빼고 실제 비용을 산정한다. 해석·인용·선호 판독 호출도 별도 비용이다.

P3은 4×100=400평가, P4는 3×500×3=4,500평가/모델의 상한 예시다. 세 조건을 세 번씩 비교하면 작지 않은 실험이다. 자동으로 전 단계 예산을 소비하지 않고 단계별 산출물을 확인한 뒤 진행한다. 이 문서를 작성하면서 해당 호출을 시작하지 않았다.

설명이 활성과 맞지 않거나 문체 차이만 포착하면 G3 대규모 최적화를 진행하지 않는다. 이때 더 큰 SAE나 NLA를 자동으로 추가하지 않고, 입력·답변 다양성·라벨 문제를 먼저 점검한다.

## 12. 무엇을 성공으로 볼 것인가

1. **방법 효과:** G3가 G2와 G0보다 FPQ 교정을 개선하면서 NFP 보존의 손실을 제한하는가. 또는 FPQ를 유지하면서 NFP를 개선하는가.
2. **평가:** FPQ/NFP Well≥4, 평균 Well, S5, 문항별 이득/손실을 함께 보고한다. 선택한 최종 prompt는 독립적인 답변 생성 3회로 비교하고 GEPA seed 변동과 구분한다.
3. **통계:** 질문/통념 그룹을 보존한 paired bootstrap과 실행별 결과를 보고한다. 허용할 NFP 손실 폭은 결과를 보기 전에 정한다. 초안은 3%p이나 표본 수가 작아 이를 입증하지 못하면 '보존됨'으로 쓰지 않는다.
4. **일반화:** 같은 통념의 문장 바꾸기만이 아니라 그룹 제외·도메인 전이를 평가한다. 기존 Cancer test는 탐색 평가라는 노출 이력을 유지한다.
5. **일반 능력:** 최종 조건으로 MedQA/PubMedQA/Medbullets/MMLU/GSM8K를 평가한다. 각 점수를 따로 보고하고 이 시험 점수를 보고 prompt를 재선택하지 않는다.
6. **SAE의 필요성:** G2와 차이가 없으면 '특징을 이용한 피드백이 유용하지만 SAE의 추가 효과는 확인하지 못함'이다. G1과도 같으면 더 많은 예시의 효과일 수 있다.

특징의 활성과 선호가 연관된다고 그 특징이 모델 실패의 인과 원인임을 뜻하지 않는다. 이번 기여 후보는 최적화에 유용한 정보를 제공하는 방법과 일반화 성능이다.

## 13. 기존 실행기와 연결할 위치

로컬 코드를 확인했다.

| 현재 코드 | 유지/변경 계획 |
|---|---|
| `external/fpqa_20261002/Well/GEPA/optimize_direct_qa.py`의 `DirectQAGEPAEvaluator.__call__` | `(normalized_score, metadata)` 반환. 점수를 유지하고 학습 샘플 metadata에만 추가 피드백 |
| `.../optimize_direct_qa_balanced.py`의 `BalancedDirectQAGEPAEvaluator` | FPQ/NFP 평가 템플릿 선택 유지 |
| `src/fpqa_well_upstream.py`의 `TransportEvaluator` | 기존 transport 유지. 원본 재현 모드를 건드리지 않는 별도 adapter 필요 |
| `scripts/run_well_upstream_cli.py` | GEPA 0.1.1 확인 및 원본 재현 실행기. 수정판은 별도 protocol/출력 폴더로 분리 |

현재 Well 실행기는 `max_metric_calls=500`, `seed=42` 기본을 사용한다. 새 조건은 동일한 고정 GEPA 버전/Well revision에서 비교한다. 단순히 metadata에 필드를 넣는 것으로 끝내지 않고, **실제로 반성 모델에 전달되는 프롬프트에 그 필드가 포함되는지 저장 로그로 확인**한다. 학습/개발 용도는 명시적인 샘플 manifest로 구분한다. 최신 GEPA 버전으로 동시에 업그레이드하지 않는다. [GEPA 공식 코드](https://github.com/gepa-ai/gepa)

구현 예정 파일(아직 실행 가능한 구현이 있다는 뜻은 아님):

- `prepare_gepa_preference_pairs.py`: 기존 결과 연결, 그룹 분할, 중복·누출 검사.
- `fit_preference_features.py`: 로컬 임베딩과 WIMHF adapter, SAE seed 반복.
- `describe_preference_features.py`: 특징 설명·검증·연관 분석과 동결 라이브러리.
- `fpqa_feature_feedback.py`: 기준 답변, 특징 점수, 인용 검증, 캐시.
- `run_gepa_feature_feedback.py`: G0–G3 실행과 비용·피드백 로그.

## 15. 그다음 NLA AO Detection DPO

- **NLA/AO:** G3에 호환 공개 모델의 내부 설명을 더한다. 동일 예시의 텍스트 설명·활성값 가림·섞기 대조를 둔다. WIMHF 임베딩 SAE를 AO에 그대로 넣지 않는다.
- **Detection:** 답변 특징이 탐지에도 유효한지 별도 검증한 뒤 판정 prompt를 최적화한다. 답변 실험과 점수·피드백·결과표를 구분한다.
- **DPO:** 검증한 특징으로 선호 쌍을 선별하고 같은 chosen의 SFT, 같은 데이터 수의 기본 DPO와 비교한다. GEPA 이득을 DPO에서도 자동으로 기대하지 않는다.

첫 완료 단위는 **자료 원장 → 동결 특징 라이브러리 → G0/G1/G2/G3 개발 비교표**다. 이 결과를 확인하기 전에는 여러 모델·내부 설명·학습까지 한꺼번에 확장하지 않는다.
